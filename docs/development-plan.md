# 水泳部タイム測定補助アプリ 開発計画

作成日：2026-11-07

## 1. 概要

水泳部の練習で行う「50m × N本（N = 20 / 30 / 40 など可変）」のタイム測定を補助するアプリ。
参加者は5〜10人。タイムを入力すると、各選手の平均タイムと前の本との差をその場で計算して表示する。
測定後は結果を表にまとめて保存し、過去の測定と比べた平均タイムの変化と、選手ごとのタイム推移グラフを表示する。

## 2. 決定事項

| 項目 | 内容 |
|---|---|
| 動作環境 | PCのブラウザのみ（キーボード入力が前提） |
| 利用者 | 1台のPCで入力・閲覧（マネージャーなど1人が操作） |
| 保存先 | PC内（ブラウザのIndexedDB）。サーバーは使わない |
| 過去比較の対象 | **距離・本数が同じ**測定のみ（例：50m×30本は過去の50m×30本と比較） |

## 3. 技術構成

- **フレームワーク**：Vite + React + TypeScript
- **データ保存**：IndexedDB（Dexie.js）
- **グラフ**：Recharts（折れ線グラフ）
- **テスト**：Vitest（計算ロジックのユニットテスト）

### データモデル

```ts
Swimmer { id, name, grade }
Session    { id, date, distance, reps, stroke, circle, memo, swimmerIds, lanes?, status, createdAt }
           // lanes: 各選手のレーン 1〜5（swimmerIds と同じ並び、未設定は null。任意）
TimeRecord { sessionId, swimmerId, rep, centis | null }   // null = 欠損（休んだ本）
```

タイムは **1/100秒単位の整数（centis）** で保存・計算する（38.52秒 → `3852`）。
小数で計算すると `38.52 - 37.33 = 1.1900000000000013` のような誤差が出るため。

### 画面構成

選手管理 / 新規測定 / 測定入力（表） / 結果 / 履歴 / 選手別グラフ / バックアップ

## 4. 機能一覧

### 4.1 選手管理
- 選手の登録・編集・削除（名前、学年［候補：1〜4年］）
- 過去の記録がある選手は削除できない（記録を守るため）

### 4.2 測定の作成
- 測定日（初期値は今日）、距離（初期値は50m）、本数N（自由入力）
- 種目・サークル・メモ（任意）
- 参加選手の選択
- 前回の設定をコピーして作成

### 4.3 タイム入力（メイン画面）
- 行が選手、列が本数の表で入力
- 入力の自動変換：`3852` → `38.52`、`10523` → `1:05.23`
- Enter / Tab / 矢印キーでマスを移動（「選手順」と「本数順」を切り替え可能）
- 入力の修正・削除、欠損（休んだ本）の扱い
- 入力途中の自動保存（アプリを閉じても続きから再開できる）

### 4.4 その場で計算して表示
- 各選手の**平均タイム**（入力済みの本だけで計算し、欠損は除く）
- 各マスに**前の本との差**（例：4本目 38.52、3本目 37.33 → **+1.19**）
  - 遅くなった（＋）は赤、速くなった（−）は青
- ベスト・ワースト・ばらつき（標準偏差）、入力済み本数 / N
- 全体の進み具合

### 4.5 結果表示
- 「測定終了」でセッションを確定（確定後も修正は可能）
- 結果表：選手 × 本数のタイム一覧と、平均・ベスト・ワースト
- **過去との比較**（距離・本数が同じ測定のみ）
  - 前回との平均タイムの差（例：−0.42秒 改善）
  - 自己ベスト平均との比較、直近数回の平均との比較
  - 改善・悪化を色と矢印で表示

### 4.6 グラフ
- 選手ごとの1本ずつのタイム推移（折れ線。横軸＝本数、縦軸＝タイム）
- 平均ラインの表示
- 複数選手の重ね表示（第2段階）
- 測定日ごとの平均タイム推移（第3段階）

### 4.7 保存・履歴
- 測定の一覧（日付・距離×本数・参加人数・メモ）、詳細表示、削除
- 選手ごとの過去の測定一覧

### 4.8 出力・バックアップ
- JSONでのバックアップと復元
- CSV出力
- 結果表の画像化（第3段階）

## 5. 実装の順序

**データの土台 → 計測当日に必要な機能 → 振り返りの機能**の順で作る。各段階が終わるたびに動かして確認する。

| 順 | 作るもの | 理由 | 完了の目安 |
|---|---|---|---|
| 0 ✅ | プロジェクトの準備、画面切り替えの枠 | すべての土台 | `npm run dev` で空の各画面に移動できる |
| 1 ✅ | **データモデルと計算ロジック**（平均、前の本との差、タイムの変換・表示形式、前回比較）＋テスト | アプリの中心となる部分。画面がなくてもテストで正しさを確かめられ、あとで画面を変えても計算が壊れない | Vitest が全部通る |
| 2 ✅ | **選手管理** | 測定を作るには選手データが必要。IndexedDBへの保存の仕組みもここで固める | 選手を登録し、再読み込みしても残っている |
| 3 ✅ | **測定の作成** | 本数Nと参加選手が決まらないと入力表を作れない | N本 × 参加人数の入力表が作られる |
| 4 ✅ | **タイム入力の表＋その場の計算表示** | 一番大事で、一番難しい画面 | キーボードだけで全マスを入力でき、平均と前の本との差が手計算と一致する |
| 4.5 ✅ | **JSONバックアップ（前倒し）** | 試しに使い始める前に、データが消えたときの備えを用意する | 書き出し → 復元でデータが元どおりになる |
| ✅ | **実際の練習で試す** | ここまでで計測当日の手計算はなくなる。入力しやすさは使ってみないとわからない | 使った人の意見を集め、5以降に反映する |
| 5 ✅ | **結果表と前回比較** | 過去のデータがたまってから意味が出る機能なので、この順番で問題ない | 2回目の同じ条件の測定で、前回との差が表示される |
| 6 ✅ | **選手別の推移グラフ** | 結果表のデータをそのまま使える | 選手を選ぶと折れ線グラフが表示される |
| 7 ✅ | **履歴の一覧・詳細・削除** | 5・6で作った「過去の測定を読み出す処理」を使い回せる | 過去の測定を開いて、結果とグラフを見られる |
| 8 ✅ | **第2段階**：CSV出力、複数選手の重ねグラフ（異常値の警告は作ったが不要となり削除） | 便利な追加機能 | — |
| 9 | **第3段階**：結果表の画像化（測定日ごとの推移グラフはフェーズAで実装済み） | あると嬉しい機能 | — |

### 進め方のポイント
- **計算ロジック（手順1）を最初に固める。** 平均や差を間違えるとアプリ全体が信用できなくなるため、テストで確かめてから画面を作る。
- **手順4のあとに一度、本番で使う。** 入力の順番（選手ごとに進むか、本数ごとに進むか）などは、実際に使って決める。
- **バックアップは早めに用意する。** データはPC内だけに保存されるため、ブラウザのデータを消すと記録も消える。

## 6. 動作確認

- N=20、選手5人で測定を作り、全マスを入力して、平均と前の本との差が手計算と一致することを確かめる
- 入力の途中でページを再読み込みし、データが残っていることを確かめる
- 同じ条件で2回目を測定し、前回比較とグラフが正しく表示されることを確かめる
- JSONで書き出し、データを消してから復元し、元に戻ることを確かめる

### フェーズCの進め方

**方針：端末に保存する今の作りは残し、クラウド（Supabase）と同期する。**
プールサイドでは電波が不安定なので、入力はこれまでどおり端末の中に保存し（オフラインでも入力できる）、
つながっているときにクラウドへ送る・クラウドから受け取る。画面はほぼ今のまま使える。

| 手順 | 内容 | 状態 |
|---|---|---|
| C0 | **下準備**：選手・測定の番号を、端末ごとに重ならないランダムな文字列（UUID）に変更。画面からのデータベース操作を `src/repo/` 経由に統一 | ✅ |
| C1 | **外部サービスの準備**（部の担当者の操作）：Supabase プロジェクトの作成、Discord 開発者ポータルでのアプリ登録、Supabase 側で Discord ログインを有効化、データベースの作り（`supabase/migrations/0001_init.sql`）の実行 | 一部済 |
| C2 | **ログインと役割**：Discord でログイン。役割（承認待ち／部員／管理者）は管理者が「部員」画面で承認・変更する。記録係は測定ごとに管理者が指名する（下記） | ✅（本物のクラウドでの確認待ち） |
| C3 | **同期**：端末の変更をクラウドへ送る・クラウドの変更を受け取る（1マス単位。同じマスは後から保存した方が残る）。電波がない間は端末にためて、戻ったら送る。ほかの端末の変更はリアルタイムで知らせを受けて取りに行く | ✅（本物のクラウドでの確認待ち） |

### 権限（`supabase/migrations/0002_recorders.sql`）

0001 の表はそのまま使い、0002 で「記録係を測定ごとに指名する」仕組みを加えた。
（Discord サーバーのロールで自動承認する案は見送り。承認は 0001 と同じく、管理者が「部員」画面で手で行う。
最初にログインした人が管理者になるのも 0001 のまま）

**記録係を測定ごとに指名する**（`sessions.recorder_ids`）
- 0001 の「入力担当」の役割はなくし、部員に読み替える
- 測定を作れるのは管理者だけ。作るとき・「測定情報を編集」で記録係を選ぶ（複数人可）
- 記録係は、その測定が入力中の間だけ、全員分のタイムの入力・修正、測定の設定の変更、測定の終了ができる
- 終了後にタイムを直せるのは管理者だけ

| 役割 | できること |
|---|---|
| 承認待ち（pending） | 何も見られない |
| 部員（member） | 記録を見る。記録係に指名された測定は、入力中の間は入力できる。入力中の測定の記録係の間は選手の登録もできる |
| 管理者（admin） | すべて（測定の作成・削除、記録係の指名、終了後のタイム修正、部員の承認・役割の変更）。複数人可。最後の1人は外せない |

- アプリの画面も役割に合わせる（`src/cloud/permissions.ts`）。記録係でない人の入力画面は「見るだけ」になる。
  クラウドと同期していない端末は、これまでどおり全部できる
- 同期で送るのは、管理者はすべて、部員は記録係に指名された測定の分だけ。それ以外の変更は送らずに取り消し、クラウドの内容に戻す
- テスト：`src/cloud/rls.test.ts`（手元の PostgreSQL で 0001 → 0002 を実行し、役割ごとに確認）、
  `src/sync/engine.test.ts`（記録係・部員の同期）

**適用の手順**（0002 はまだ Supabase に適用していない）
